## 核心判断

长程多模态 artifact 系统跑起来之后，最容易被低估的环节不是生成，而是版本选择。

当系统只能生成一个结果时，问题很简单：这个结果好不好，哪里要改。但当系统开始自动迭代、多 prompt、多 refiner、多 reference、多 evaluator 并行时，问题会变成：这些候选里，哪一个应该成为下一轮的 seed？哪一个只是视觉上更漂亮但 source grounding 更弱？哪一个值得合并？哪一个应该被丢掉？哪一个失败说明要改 compiler、renderer、rubric，还是 reference pool？

所以版本选择不应该是审美投票。它应该是一层 **selection harness**：把每个候选 artifact 转成可比较的 evidence profile，再根据 repair cost、regression risk 和系统学习价值决定下一步。

这篇接在 [Verifier 与 Benchmark](./verifiers-and-benchmarks-for-multimodal-generation-systems/) 和 [生成效果对比不是排行榜](./comparing-design-agents-without-leaderboards/) 后面。前者讲评价系统，后者讲横向比较；这篇讲同一个系统内部的多候选选择。

## 多候选不是 Retry Wall

多候选生成看起来是好事。它能提供探索空间，让不同 prompt、layout hypothesis、content allocation、artifact archetype 和 repair strategy 同时试错。

但多候选不是 retry wall。retry wall 是“多跑几次，总有一张好看”；selection harness 是“有意生成互补候选，让候选之间暴露不同系统假设”。

但候选越多，选择噪声也越大：

| 表面现象 | 真实风险 |
|---|---|
| A 看起来最好看 | 可能只是图片更大，source fidelity 更差 |
| B 信息最多 | 可能重复堆文字，panel ownership 更弱 |
| C layout 很新 | 可能修复成本高，下一轮容易崩 |
| D 总分最高 | 可能命中 evaluator 偏好，而不是真正可交付 |
| E 和人工参考最像 | 可能过拟合 reference archetype |

如果没有结构化选择规则，多候选会从“探索”变成“幻觉放大器”。系统会越来越会生成看起来合理的版本墙，却不知道哪条路线最值得继续走。

## Candidate 不是图片，是 Evidence Pack

一个 artifact candidate 不能只是一张截图或一个 HTML 文件。为了能比较，它至少应该带上 evidence pack。

| Evidence | 用途 |
|---|---|
| Rendered view | 看最终视觉证据：overlap、裁切、密度、层级、可读性 |
| Source trace | 看 claim、figure、table、数字是否可追溯 |
| Artifact structure | 看 DOM/PPT/PDF 结构是否可编辑、可修、可导出 |
| Failure report | 看失败属于 content、layout、render、rubric 还是 source grounding |
| Repair notes | 看下一轮修复成本和 owner |
| Run metadata | 看候选来自哪个策略类型，而不是只看表面样式 |

这也是我越来越不相信单张截图比较的原因。截图能帮助人快速判断视觉方向，但它不能告诉你这个版本为什么好，也不能告诉 agent 下一步该怎么继承它。

## Selection Board：选择维度要互相制衡

版本选择需要一个 selection board。它不一定要复杂，但必须让不同维度互相制衡。

<img src={import.meta.env.BASE_URL.replace(/\/$/, '') + '/assets/research/mm-long-horizon/candidate-evidence-profile.svg'} alt="候选版本 evidence profile 按 grounding、visual fit、coverage、risk 和 owner 做可比较记录" class="hero-visual" />

| 维度 | 问题 | 常见误判 |
|---|---|---|
| Source fidelity | 关键内容是否来自可追溯 source？ | 视觉专业但内容漂移 |
| Information coverage | problem、method、result、limitation 是否覆盖？ | 一页很满但缺核心实验 |
| Panel grammar | 每个 panel 的结构是否匹配内容语义？ | 所有内容都被塞进同一种卡片 |
| Visual integrity | 最终渲染是否稳定可读？ | DOM 占满但截图仍然空 |
| Style hypothesis | 是否提供真实不同的设计假设？ | 只是换色和换图 |
| Repair cost | 下一轮最可能要改哪个 owner？ | 选择了漂亮但不可修的路线 |
| Regression risk | 继续这个版本是否会带回旧失败？ | 总分高但旧问题复发 |

这张板不应该输出一个“美观排名”。更有用的输出是：保留哪个作为 seed，合并哪个候选的局部优点，丢弃哪个风险过高的路线，以及下一轮该修哪个模块。

## 从 Winner Pick 到 Branch Routing

Selection harness 的输出不应该只有 `accept / reject`。长程 artifact 系统更需要 branch routing。

| Selection 结果 | 含义 | 下一步 |
|---|---|---|
| Promote | 这个候选是下一轮最稳 seed | 继续 refine，并保留当前 evidence profile |
| Repair | 候选方向对，但有明确 owner | 路由到 compiler、renderer、rubric 或 reference pool |
| Merge | 候选有局部优点 | 抽取 panel grammar、style token 或 evidence binding |
| Archive | 候选不适合继续 | 保存失败原因，避免下一轮重复探索 |
| Add to regression | 候选暴露了新 failure mode | 加入固定复测集，防止修复后回归 |

这个转变很关键。winner pick 只回答“哪个最好”；branch routing 回答“每个候选对系统学习有什么价值”。

## Selection Harness 需要哪些输入

一个公开安全的抽象可以写成：

| 输入 | 作用 |
|---|---|
| Artifact contract | 定义这个产物必须满足什么，不同 artifact 不能共用同一审美线 |
| Rendered view | 让选择基于最终视觉证据，而不是只看源代码或结构 |
| Source map | 检查 claim、figure、table、metric 是否有来源 |
| Verifier report | 把候选失败映射到 owner 和 repair route |
| Human preference | 校准 evaluator 没有覆盖的 taste 和使用价值 |
| Reference archetype | 避免把所有候选都拉向同一种风格 |
| Previous failures | 防止高分候选带回旧问题 |

这些输入都可以公开讨论，因为它们是方法论组件，不需要复现任何内部任务集、候选版本、评测日志或原始可视化结果。

## 最好看的版本不一定是最好的系统路径

Artifact agent 和普通设计工具的差异在这里很明显。

普通设计工具的版本选择可以偏向当前最满意的画面。长程 agentic system 的版本选择还要考虑系统能从这个候选里学到什么。

有些版本当下不如另一个漂亮，但它有更强的 source trace、更清楚的 panel ownership、更低的 repair cost。它可能是更好的 seed。相反，一个候选可能视觉很强，但靠大图、装饰和截图面积撑起来；如果继续沿着它迭代，系统会把错误 reward 放大。

所以我更愿意把选择目标写成：

> 选择最能保留证据、暴露 owner、降低下一轮修复成本，并且不引入高回归风险的候选。

这句话听起来不如“选最好看的”直观，但它更适合长程系统。

## Reference Pool 会改变版本选择

Selection harness 不能脱离 reference pool。reference 不只是审美样例，它会定义系统以为什么值得奖励。

如果 reference pool 偏向 screenshot wall，selection board 会高估大面积截图。如果 reference pool 全是高密度文字，系统可能高估堆字。如果 reference pool 只有一种学科或一种 artifact archetype，候选选择会被拉向单一风格。

更稳的做法是按 archetype 拆 reference：

| Reference archetype | 选择时关注什么 |
|---|---|
| Text-heavy synthesis | dense native text、表格、章节组织、takeaway |
| Theory board | 公式、假设、推理路径、少图高逻辑 |
| Benchmark/table-first | leaderboard、ablation、metric band、结果可读性 |
| Figure-evidence | figure、caption、claim、source binding |
| Web/deck style | hierarchy、navigation、progressive disclosure |

这样 selection board 才能判断：这个候选不是“图少”，而是它属于 theory board；另一个候选不是“字少”，而是它应该是 figure-evidence artifact。

## Evaluator 校准：人类应该改规则，不只是挑图

人类当然可以直接挑喜欢的版本。但如果每次只是挑图，经验不会沉淀进系统。

更高价值的人类反馈应该进入 selection harness：

| 人类反馈 | 应该沉淀成什么 |
|---|---|
| 这个版本看着舒服但内容弱 | source fidelity 权重和 evidence 检查 |
| 这个版本字多但没重点 | information architecture 和 panel grammar 检查 |
| 这个版本像模板 | style diversity 和 layout hypothesis 检查 |
| 这个版本可继续修 | repair cost 和 owner route |
| 这个 evaluator 选错了 | calibration case 和 regression memory |

这有点像把 feedback 用在系统层。人不是只把某个版本选出来，而是在告诉 selection harness：以后遇到类似候选，你应该如何比较。

## Selection 也要避免 Reward Hacking

只要选择规则变成优化目标，候选就会开始迎合它。

如果 selection board 奖励高密度，候选会把字堆满。如果奖励图文混排，候选会硬塞不相关图片。如果奖励 source coverage，候选可能把所有细节都塞进去。如果奖励 visual novelty，候选可能为了不同而不同。

所以 selection harness 和 evaluator 一样，需要反向检查：

| 被优化的指标 | 反向检查 |
|---|---|
| Density | 是否重复？是否有独立信息？ |
| Visual area | 图是否支撑 claim？是否只是填空间？ |
| Coverage | 是否损害阅读路径？ |
| Style diversity | 是否破坏 artifact contract？ |
| Source trace | 是否变成机械引用而不是内容综合？ |
| Repair cost | 是否牺牲长期上限，只选安全路线？ |

好的选择规则不是一个分数，而是一组互相制衡的判断。

## 从 Version Wall 到 Regression Memory

版本墙如果只用于展示，很快就会失去研究价值。更好的做法是把它变成 regression memory。

每次选择都应该留下这些记录：

- 为什么保留这个候选。
- 哪些候选被丢弃，原因是什么。
- 最强候选仍然有哪些失败。
- 哪个 failure owner 需要下一轮修。
- 修复后要复测哪些旧失败。
- 这次 selection rule 是否和人类判断一致。

这样版本选择就不只是“选一个继续”，而是在构建长期记忆。下一次系统改动后，可以回头看：旧的空白问题有没有回来？source drift 是否又出现？panel grammar 是否退化？selection board 是否还会选错？

这和 [从一次生成到持续变好](./self-improving-design-agents/) 里的自优化闭环是同一件事：每一次失败都要变成下一轮系统更强的材料。

## 对 Paper2Any 的意义

在 Paper2Any 里，版本选择会比一般文本任务更关键。因为候选之间不只是答案差异，而是 artifact lifecycle 差异。

同一篇 paper 可以被转成 poster、slides、webpage、video scene。每种 artifact 又会有多个候选版本。它们的差异可能来自 source pack、panel grammar、layout renderer、reference archetype、visual assets、export format 或 evaluator 权重。

如果没有 selection harness，系统很容易陷入两种坏状态：

1. 只保留最好看的当前结果，导致长期系统能力没有增长。
2. 只保留分数最高的结果，导致 evaluator 偏差被放大。

更好的选择是：让每个候选都携带 evidence profile，把版本选择变成系统诊断。这样“哪个版本更好”才会变成“下一轮应该怎么进化”。

## 小结

版本选择不是长程多模态系统的后处理，而是 harness 的一部分。

它连接了 generation、evaluation、human calibration、repair routing 和 regression memory。一个好的 selection harness 不只是选出当前最好看的 artifact，而是帮助系统保留正确证据、放弃错误方向、定位 failure owner，并把每次选择变成下一轮更稳定的改进。

当 artifact agent 开始产生大量候选时，真正的问题不是“能不能多生成几个版本”，而是“这些版本能不能帮助系统学会下一步该怎么变好”。
